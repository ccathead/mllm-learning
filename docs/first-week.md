# 第一周：从单图到可比较的基线

## 1. 跑通一张图

- 云端创建独立环境，按 [LLaVA HF 文档](https://huggingface.co/docs/transformers/model_doc/llava) 运行 `llava-hf/llava-1.5-7b-hf` 的官方示例。
- 使用一张自己的图片；确认输入路径、processor、聊天模板及生成参数。
- 保存自己运行成功的命令与脚本到 `src/`，配置放到 `configs/`。
- 记录 GPU、显存峰值、模型 revision、PyTorch/Transformers/CUDA 版本和耗时。
- 先单图、短输出，再扩大批次；实例规格以实测决定，显存需求待核验。

**验收：** 换图、换问题可以独立运行；说明从输入图片到模型回答经历了哪些步骤。

## 2. 建立固定测试集

- 先收集 30 张可使用的商品图片，再逐步扩到约 100 张。
- 覆盖清晰图片、小字、遮挡、多物体，以及图中无法确定的字段。
- 固定字段：`category`、`color`、`visible_text`。字段含义、同义词规则及无法确定的标注规则先写清楚。
- 每张图填写参考答案，标注来源和 `product_id`；同一商品的不同照片归到同一划分。
- 图片与标注放在忽略提交的 `data/`；仓库只提交数据说明、版本和校验摘要。
- 示例结构是自己的评测格式，训练时再转换为选定框架的格式：

```json
{"id":"sample-001","image":"data/images/001.jpg","product_id":"product-001","split":"test","reference":{"category":"杯子","color":"白色","visible_text":"无法确定"}}
```

## 3. 批量推理与记录

- 用同一提示词、生成设置和模型 revision 跑完所有图片。
- 保存每条原始回答、解析结果、耗时与失败原因；不要丢弃格式错误的样本。
- JSON 有效率 = 可解析且满足约定字段/类型的回答数 / 全部样本数。
- 字段准确率 = 正确字段数 / 全部应评测字段数；解析失败按错误计，原始回答可另做人工分析。
- 对标注“无法确定”的字段，单独统计编造具体答案的比例，并注明分母。
- 摘出 10 个失败案例，按感知、文字识别、指令遵循、格式、无法确定时编造进行人工分类。

**验收：** 一份完整基线报告、10 个案例、可再次运行的脚本与配置。训练前先保留这份基线。

## 4. 开始源码拆解

HF 推理先读安装版本的 Transformers LLaVA 实现；再对照官方 LLaVA，避免将两套实现当作同一调用链。

- 官方源码入口：[llava_arch.py](https://github.com/haotian-liu/LLaVA/blob/main/llava/model/llava_arch.py)。
- 跟踪预处理 → 视觉编码 → projector → 多模态序列 → generate。
- 实际打印一张图的张量形状，记录函数路径、commit 和证据。
- 做一个小改动：替换图片或遮挡关键区域，观察回答变化并解释原因。
